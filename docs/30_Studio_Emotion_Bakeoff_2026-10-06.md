# 스튜디오 감정 파생 실험 — 연, 2026-10-06

관측일·기록일: 2026-10-06. 사용자 지시로 실제 공급자 요청을 실행했다. 이 문서는 실험 결과이며 제품의 모델 교체나 UI 승인 기록은 아니다. 선행 분석은 [docs/29](29_Studio_TTS_Preimplementation_Review.md).

## 1. 결론과 구현 방향

**이번 조건에서는 Ideogram으로 일괄 교체할 근거가 부족하다. Qwen의 연출 지시와 WF-2/FaceDetailer의 재생성을 함께 개선하는 편이 타당하다.**

- Qwen은 감정을 잘 전달하지만, 짧은 표정 지시·자세 고정에서도 기쁨의 큰 눈감은 웃음과 당황의 과도한 눈 확대가 남았다. 저장된 동작 지시만이 원인은 아니다.
- Ideogram Precise Edit는 외형 보존이 강했지만 감정 변화가 약했다. Low 기쁨·수줍음, Medium 기쁨은 **neutral과 디코딩된 RGB 픽셀 전체가 동일**했다. 이는 감정 편집이 이뤄지지 않은 결과다.
- 현행 WF-2는 표정·눈매·머리/의상 세부를 다시 해석했다. FaceDetailer에서도 눈·입·얼굴의 점 표현이 달라졌다. 최종 Ideogram 결과에 웃음이 있다고 해서 Ideogram의 표정 편집 성공으로 판단할 수 없다.
- 자세 고정은 원인 확인용이다. 최종 제품은 **캐릭터에 맞는 작은 제스처 하나와 통제된 표정 강도**를 목표로 한다. 현행 A의 모든 동작이 나쁜 것은 아니며, 특히 분노의 양주먹·이악물기가 과장됐다.

후속 구현 후보는 짧은 표정·낮은 연출 강도·작은 제스처를 별도 지시하고, 감정 파생의 재생성 후처리를 생략하거나 강도를 낮출 수 있게 하는 구성이다. 단, 이번 실험은 후처리 생략의 완성품 품질이나 새 지시의 효과를 검증하지 않았다. WF-3 배경 제거·최종 앱 표시도 미실행이다.

같은 좌표의 얼굴 영역 `(335,125)–(685,425)` 밖에서 RGB 채널 최대 차이가 8/255보다 큰 픽셀의 비율을 계산했다. 5감정 평균은 A **11.15%**, B **2.91%**, C/D **0%**다. 전체 디코딩 픽셀 일치가 100%인 결과는 `C_joy`, `D_joy`, `C_shy` 3건이다.

## 5. RunPod 정지 원인과 복원

실험 시작 때 운영 `lucid-ugc` endpoint는 `workersMin=0`, `workersMax=0`이었다. 첫 후처리 POST 2건은 HTTP 409/no request ID로 거절됐다. endpoint health의 완료/실패/queue 수가 그대로였음을 확인해 미접수 원장을 보존하고, 사용자 “후처리까지 실행해라” 승인 후 같은 payload로 제출했다.

실행 중 설정은 0/0→0/1, 이후 cold start를 위해 1/1로 임시 변경했다. 작업이 전부 끝나고 queue/inProgress=0을 확인한 뒤 **0/0으로 복원**했다. 최종 endpoint 설정은 최초 스냅샷과 전체 일치한다. 이미지/GPU 종류/템플릿/다른 설정은 바꾸지 않았다.

운영 DB의 원시 집계에서 마지막 제작 job 생성은 `2026-09-04T15:16:55.331627`, 마지막 READY 갱신은 `2026-09-04T15:51:51.930454`였다(응답에 timezone offset 없음). [RunPod 공식 문서](https://docs.runpod.io/serverless/endpoints/endpoint-configurations)에 따르면 3일간 미사용 시 max=2, 7일간 미사용 시 max=0으로 자동 축소되며 직접 올리기 전에는 0을 유지한다. 따라서 **미사용 자동 정지가 가장 유력한 설명**이나, 운영 DB의 제작 기록은 모든 직접 API 요청 이력이 아니며 설정 변경 행위자/이력은 읽지 못했다. 수동 정지나 다른 자동 조치를 배제한 확정 원인은 아니다.

복원 이후 최신 serverless worker 목록은 `total=0`, `running=0`, `workers=[]`였다. `/health`의 worker running 집계는 1이 잔존했으므로 실제 목록과 구별한다. 완료 jobs는 1211→1231, failed 9/retried 1은 그대로, queue/inProgress=0이다.

현재 원복 상태는 UGC 요청을 받을 수 없는 max=0 상태다. 다음 운영 사용/배포 때 가동 용량을 별도로 설정해야 한다. 이번 임시 실행 승인을 상시 가동 승인으로 해석하지 않았다.

운영 확인 중 이전 GraphQL worker 목록의 배열을 잘못 출력해 **워커 환경의 R2 자격정보와 워커 전용 secret이 이 세션 도구 출력에 노출되는 실수**가 있었다. 갤러리·정본문서에는 포함하지 않았고 실제 값을 재인용하지 않는다. 이 출력은 삭제하지 못했으며 키 회전은 미실행이다. 해당 자격정보 교체 검토가 필요하다.

## 6. 최종 대조와 재현 자료

- 원장 40슬롯의 누락/중복/미확정 0. provider별 request ID 20고유. raw20 + WF-2 20 + detail20 = **60**이며 전부 1024², 요청 SHA/이미지 SHA/원장 metadata 대조 통과.

- 프로덕션 fixture·워크플로/상수 변화 0, 기존 neutral·5감정·base 원본 **7/7 SHA 동일**. 캐릭터 자산·DB·에너지·웹훅을 변경하지 않았다.
- 동결 manifest 정상 통과 및 누락/중복/다중 생성/model/source 변조·반복POST·잘못된 인증 host 거절 검증 완료. 실제 endpoint max0의 HTTP409도 원장에 남겼다.

1. 감정에 맞는 적당한 몸동작은 유지한다. 완전 자세 고정/얼굴 전용 편집을 최종 기본값으로 확정하지 않는다.
2. UGC 생성 시 캐릭터마다 맞는 감정 바리에이션을 동적으로 만들고 영속화하며 시스템 프롬프트에 허용 repertoire를 넣는다. 공통 15종 고정만의 밋밋함을 개선한다.
3. 이미지 실험 뒤 **스튜디오→TTS** 순으로 구현한다.
4. TTS 자동 모드에서는 LLM이 표시 대사와 별도로 연기 태그가 포함된 TTS 입력 필드를 출력한다. 수동 듣기는 별도 변환으로 입력을 만든다. 모델은 환경변수로 관리하며 v4/Turbo 품질 비교는 구현 후 사용자가 직접 한다.

스튜디오 동적 repertoire는 Character에 필드 하나를 추가하는 것 외에 `EmotionTag` enum·생성 완료 개수·asset 이름·publish/reroll·chat scene DTO·FE lookup까지 계약을 연결해야 한다. 제안은 안정된 `expressionId`와 의미 감정 축을 나누고, neutral 필수·기존 공식/UGC15종 fallback을 유지하며 캐릭터별 허용 ID만 선택하게 하는 구성이다. 개인화가 단순히 공통15종의 표시 이름만 바뀌는 구현이 되지 않도록 한다. 생성 개수/비용 단위/편집 UI는 구체화하고 화면이 크게 바뀌면 승인 가능한 목업부터 준비한다.

현재 단계는 실험 완료이며 제품 소스 구현·가격 확정·키 회전·커밋/푸시/배포는 아직 하지 않았다.
