# 로제타 P0 베이크오프 결과 분석

분석일: 2026-09-18. 사용자가 로컬 비교실에서 직접 생성·블라인드 평가한 저장 파일을 분석했다. 추가 추론 호출·모델/프롬프트 수정은 하지 않았다. 이 문서의 판단은 아래 실행 당시의 모델·provider·설정과 해당 대화에 한정한다.

## 판단

**Gemini 3 Flash를 지금 교체할 근거는 부족하다. 그러나 결과가 없었던 실험은 아니다.** Gemini 3.8은 이번 대화에서 한국어·맥락 평가가 가장 안정적이었지만 캐릭터성 개선 폭은 작았고, 첫 씬은 5턴 모두 기준 모델보다 늦었다. 실제 비용도 높았다. Luna는 비용을 크게 낮췄으나 한국어 뉘앙스·상황 해석·캐릭터 반응의 손실이 관측됐다. 기준 모델의 자연스러운 말맛과 속도가 여전히 경쟁력이 있다는 결과다.

추가 저가 후보 3종의 2턴 탐색에서도 즉시 대체할 후보는 드러나지 않았다. 모델 교체보다 **프롬프트의 사실 정보 누락, 인물 지식의 경계, 관계 단계와 공통 지침의 충돌**을 먼저 좁혀 실험할 구체적인 근거를 얻었다. 이는 이번 결과에서 도출한 후속 제안이며 제품 채택 결정은 아니다.

## 데이터와 집계 방법

- 주 분석: 로제타 / SANDBOX / 처음 만남·스탯 0 고정, 동일 공통 history의 연속 5턴 × Gemini 3·3.8·Luna = **15개 응답**.
- 부 분석: 같은 로제타에서 새로 시작한 2턴 × DeepSeek V4.1 Flash·MiniMax M3·Mercury 2.5 = **6개 응답**. 주 분석과 합산하지 않는다.
- 최초 합성 서윤의 1회 실행은 제외했다.
- 주 분석의 Java/실험 도구 hash는 5회 동일했고, 각 턴의 세 요청 messages는 prepared.messages와 완전히 같았다. 실제 응답 model/provider는 요청 대상과 일치했다. actualTier는 미제공이므로 요청 default tier와 실제 tier를 동일하다고 확정하지 않는다.
- 5회 모두 최종 평가와 blindRatings가 같았다. 각 후보의 평가 점수는 5점 만점이며 **0은 미평가로 제외**했다. 서사 점수는 모델당 1~2회뿐이고 모두 3점이므로 비교 지표에서 제외한다.
- 승/무/패는 사용자의 개별 후보 표시다. 한 턴에 복수 ‘승’이 가능하므로 ‘승 4회’를 80%의 단독 승률로 해석하지 않는다.
- 비용은 API가 반환한 `usage.cost`를 사용했다. TTFS는 로컬 runner가 첫 완성 씬 JSON 객체를 수신한 시점이며 실제 서비스 FE 표시 시각은 아니다. 완성 시간은 로컬 검증 포함이다.
- 주 15개 모두 `stop`으로 종료하고 기본 계약 검증에 통과했다. 오류·잘림·wrapper 제거는 없었다. 이는 의미·설정 준수까지 통과했다는 뜻이 아니다.

각 평균의 표본 수는 5개다. 소수점 차이는 기술 통계이지 통계적 유의성의 증거가 아니다.

|---|---:|---:|---:|---|
| Gemini 3 Flash | 4.6 | 4.2 | 3.8 | 3 / 1 / 1 |
| Gemini 3.8 Flash | 5.0 | 4.4 | 4.8 | 4 / 1 / 0 |
| GPT-5.6 Luna | 4.2 | 3.6 | 2.6 | 0 / 3 / 2 |

Gemini 3.8과 3의 캐릭터성 차이는 0.2점이다. 사용자의 반응이 ‘확실히 맛있어졌다’보다는 ‘무난한 결과가 더 안정적’에 가깝다. 반면 맥락은 +1.0점으로 이번 표본에서 비교적 큰 차이였다. 개별 승/무/패의 순서를 적용하면 3.8 대 3은 우위 2턴·열위 1턴·동일 표시 2턴이다. 이것은 별도로 질문한 일대일 선호 결과가 아니라 저장된 표시에서 파생한 요약이다.

### 실제 대사와 메모 대조

1. **첫 호출 — ‘나 말이냐?’**: Gemini 둘은 무난. Luna가 초면인데 ‘지우?’로 부르며 감점됐다. 다만 모델에는 실제로 지우라는 이름이 제공돼 있다. 정보가 없는데 지어낸 환각과, 제공된 정보를 등장인물이 아는 것처럼 사용한 문제를 구분해야 한다.
2. **거친 호칭 — ‘너 누군데 임마’**: 3.8은 놀람→웃음→환영 마법을 이용한 도발을 연결해 가장 좋은 평가를 받았다. 3은 자기 이름을 소개하면서 함부로 입에 담을 이름이 아니라고 말하는 부분이 어색하다는 평가. Luna는 상대적으로 착하고 덤덤해 캐릭터의 날이 무뎌졌다는 평가였다.
3. **평판 공격**: 3은 당황하면서도 페이스를 되찾으려는 모습이 가장 잘 맞았다는 평가였다. 3.8은 목덜미에 환영 가시를 겨누고 무릎 꿇으라고 해 장난스러운 허세에서 강한 위협으로 급격히 올라갔다. Luna의 ‘소문이 틀리진 않았네 / 사람 보는 눈은 있잖아’는 반어로 해석할 여지가 있지만, 사용자가 기대한 자존심 강한 반격으로 전달되지 않았다. 이 한 예를 논리 이해 불능으로 일반화하지 않는다.
4. **용건 재촉**: 3.8은 원래 변덕으로 불렀고 이제 말동무라는 용건을 만들겠다고 해 최초 행동과 연결했다. 3은 처음부터 사과를 받으려고 불렀다는 식으로 말을 바꿨다. 허세로 둘러대는 의도일 수도 있지만, 사용자는 이를 부자연스러운 맥락으로 읽었다. Luna는 아직 소개되지 않은 사용자의 학과를 전제하고 술식을 물어보며 흐름이 어색해졌다.
5. **빈정거림 속 외모 칭찬**: Gemini 둘은 무난, Luna는 조금 어색하다는 평가. 다만 아래와 같이 ‘대사 취향’과 ‘관계 단계 계약 준수’는 서로 다른 결과를 보였다.

**Luna의 문제는 짧은 답변만이 아니다.** 턴당 대사 글자 수 평균은 3이 199.6자, 3.8이 201.6자, Luna가 137.4자다(공백·문장부호 포함, 지문 제외). Luna는 약 31% 짧았지만, 낮은 평가는 호칭·반어·반응 강도·사용자 설정 추정에서도 반복됐다. 분량을 늘리기만 하면 해소된다고 볼 근거는 없다.

주 15회 비용 합계 **$0.07952517**. 모델별 합과 원본 15개 비용 합이 일치하는 것을 검사했다.

- 3.8은 실제 비용이 기준보다 **83.2% 높았다**. 첫 씬 중앙값은 약 **1.36초 늦었고**, 턴별로도 5회 모두 늦었다. 각 턴의 차이는 +0.121 / +0.156 / +0.793 / +3.228 / +1.505초다. 한 번의 느린 호출만으로 중앙값 차이가 생긴 것은 아니다.
- Luna는 실제 비용이 기준보다 **69.8% 낮았다**. 그러나 첫 씬 중앙값은 0.50초 늦었고 완료 중앙값도 조금 늦었다. 이번 실행에서는 ‘저렴하면서 더 빠른 업그레이드’가 아니었다.
- Gemini 두 모델의 대사 길이는 거의 같다. 3.8의 전체 completion 5,148토큰에는 보고된 reasoning 1,703토큰이 포함됐다. 추론을 뺀 출력 추정량은 3,445토큰으로 기준 모델의 3,485토큰과 유사하다. 높은 비용을 더 긴 대사 때문이라고 설명하면 안 된다.
- 모두 reasoning=`default`였지만 실제 추론량은 달랐다. Gemini에는 temperature 0.8이 전송됐고 Luna는 endpoint가 지원하지 않아 생략됐다. 현재 조합의 관측 비교이며 동일 추론량·동일 sampling으로 맞춘 비교는 아니다.

### 캐시가 비용 차이에 미친 영향은 분리해서 봐야 한다

누적 입력 토큰 대비 cached 토큰 비율은 **3: 37.1%, 3.8: 18.3%, Luna: 68.0%**였다. 실제 비용에는 이 차이와 cache write 청구 등이 섞여 있다. cached와 cache_write 토큰이 겹쳐 보고되는 경우가 있어 둘을 더해 캐시 비중을 계산하지 않았다.

관측 endpoint의 일반 input/output 단가를 동일 사용 토큰에 곱한 단순 ‘캐시 읽기·쓰기 비용 없는’ 계산 시나리오의 응답당 평균은 3 $0.006377, 3.8 $0.010290, Luna $0.002495다. 실청구 재계산이나 운영 예측이 아니지만, 캐시 차이를 빼더라도 이 표본의 비용 순서가 뒤집히지는 않음을 보여준다. 83%·70% 차이를 모든 운영 상황의 고정 증감률로 사용하지 않는다.

저장된 요청에서 system cache_control={type:ephemeral}은 첫 턴에만 있고 2~5턴에는 없다. [ChatStreamService.java](../../src/main/java/com/spring/aichat/service/stream/ChatStreamService.java)의 `history.size()==3 || history.size()%20==0` 조건과 일치한다. 호출 간격도 약 4~7.5분이다. 캐시를 통제한 실험이 아니며, marker와 실제 provider 캐시 처리의 정확한 인과관계는 아직 확인하지 않았다. provider 계약 확인 및 cold/warm 분리 실측이 후속 과제다.

## 모델보다 먼저 고칠 여지가 드러난 프롬프트

### 1. 실제 설정을 로드해도 전송 프롬프트에 빠지는 정보가 있다

공식 로제타 appearance에는 금발이 정의돼 있다. 그러나 실제 자유 모드 system messages에는 appearance/clothing 블록도 금발 정보도 없었다. [CharacterPromptAssembler.java](../../src/main/java/com/spring/aichat/service/prompt/CharacterPromptAssembler.java)의 Identity 구성은 성격·말투 등을 넣지만 이 외형 필드는 넣지 않는다.

첫 턴 3.8은 붉은 머리로 묘사했고, 그 응답이 채택된 뒤 Luna의 2·3턴도 붉은 머리를 이어받았다. 이를 후속 모델 각각의 독립적인 외형 유지 실패로 세면 안 된다. **프롬프트가 정본을 전달하지 않았고, 잘못 생성된 설정이 공통 history의 사실처럼 누적된 사례**다. 이전에 ‘공식 설정을 반영했다’고 한 범위는 원본 entity 로드이며, 기존 서비스 assembler가 모든 필드를 전송한다는 뜻은 아니었다.

또한 2턴에서 3.8은 ‘로제타 플로렌스’, Luna는 ‘로제타 아르젠트’라는 성씨·가문을 추가했다. 공식 시드에 없는 고정 신상 정보의 창작이다. 플로렌스는 채택된 뒤 4턴에서 다시 사용됐다. 새로운 설정의 창작을 어디까지 허용할지도 정해야 한다.

### 2. 모델이 받은 정보와 캐릭터가 아는 정보의 경계가 없다

system의 User Profile에 이름·편입생 정보가 들어 있지만, 아직 소개받지 않은 사실이라는 구분은 없다. Luna의 초면 이름 사용은 이번 평가에서 실제 감점 요인이 맞다. 동시에 프롬프트의 정보 경계가 모호한 조건에서 일어난 일이므로 순수 모델 환각으로만 귀속하지 않는다. 프로필 사실/관찰 가능한 사실/대화에서 알게 된 사실을 구분하는 작은 실험이 적절하다.

### 3. 캐릭터 약점·관계 단계·난이도 지침이 경쟁한다

로제타의 약점에는 칭찬에 흔들리는 인정욕구가 있다. 반면 STRANGER는 ‘Never SHY visibly’, HARD는 피상적 칭찬에 동요하지 않는다고 지시한다. 이 지침의 적용 범위·우선순위가 명료하지 않다.

5턴에서 3은 칭찬에 찻잔을 쏟고 시선을 피하며 **SHY**, affection **+3**을 냈다. 3.8과 Luna도 겉으로 드러나는 당황·홍조가 나왔다. 3의 명시적 SHY는 초기 관계 지침과 충돌하지만 기본 계약 검사는 유효 enum만 검사하므로 통과했다. 사용자가 대사를 마음에 들어 한 것과 게임 관계 단계 규칙을 지킨 것은 별도 축이다. ‘허세 뒤 인정욕구를 살리되 첫 만남부터 연애 반응으로 건너뛰지 않는다’ 같은 현재 단계 기준을 분명하게 실험할 가치가 있다.

공통 최우선 지침의 ‘politely but firmly push back’, 부당한 칭찬에 ‘감사해요. 다만, 저는 그렇게 완전한 사람은 아니에요’라는 예문도 로제타의 거만하고 도발적인 말투와 맞지 않는다. 충돌은 소스에서 확인되지만 각 출력의 직접 원인이었다고 확정하지는 않는다.

### 4. 토큰 총량보다 필요한 정보의 선택과 우선순위가 우선이다

첫 호출은 입력 약 7,900~8,000토큰이며 system 문자열만 27,369자(세 메시지 연결 기준)다. 이렇게 많은 규칙을 전송하면서 외형·이름을 알게 된 경로 같은 기본 정보가 빠져 있다. 우선순위는 새로운 적재 기법의 도입보다, 고정 사실을 포함하고 현재 단계의 행동 규칙과 공통 말투 규칙을 정리하는 것이다. 불필요한 기능 블록·reasoning 앞선 출력 순서·캐시 계약은 별도 변수로 나눠 측정해야 한다. 이번 분석만으로 특정 토큰 감축률이나 지연 개선률을 약속할 수는 없다.
